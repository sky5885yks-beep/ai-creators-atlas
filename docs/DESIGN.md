# 设计文档：中文 AI 创作者 · GitHub 地图

- 版本：v1.0
- 日期：2026-11-23
- 在线：<https://37lfc0vis820xyiwbbv.traesite.cn/>（仅自己可见）

---

## 1. 定位

### 1.1 问题

GitHub 的 star 榜擅长回答“哪个仓库火”，但回答不了“我应该跟谁”。中文 AI 社区的信息分散在公众号、X、B站、博客和 GitHub，缺少一个以创作者为主体的入口。

### 1.2 方案

以人为节点，以分类和主阵地为筛选维度，以代表项目为落到 GitHub 的跳板。一句话：

> 跟着人找入口，而不是在 star 榜里捞针。

### 1.3 目标用户

- 想系统跟踪中文 AI 创作者的学习者；
- 想找特定方向（Prompt、Agent、工具）作者的研究者；
- 想了解某个创作者代表项目的开发者。

### 1.4 非目标

- 不做全量创作者数据库；
- 不做实时 GitHub 排行榜；
- 不做内容聚合/全文检索；
- 不做账号体系与收藏。

---

## 2. 信息架构

```
Header（品牌 / 搜索 / 视图切换）
  └─ Hero（主张 / 副标题 / 数据快照）
      └─ Stats（创作者数 / 项目数 / 分类数）
          └─ 分类 Chips
              └─ 主阵地 Chips
                  └─ 排序
                      ├─ Board（按分类分组的创作者卡片墙）
                      └─ Rank（按 followers 排序的榜单 table）
                          └─ Modal（创作者详情）
Footer（收录口径 / 快照日期）
```

设计意图：

- 首屏先给“为什么按人找”的主张，再给可操作筛选；
- 卡片墙承担浏览，榜单承担比较；
- 详情用弹层，避免离开上下文；
- 页脚明确数据口径，降低误解。

## 3. 数据模型

### 3.1 分类 `CATS`

```js
{ id: "tutorial", no: "01", title: "教程科普", desc: "系统课、逐段精读与概念科普，适合打基础。" }
```

5 个分类及数量：

| id | 标题 | 创作者数 |
| --- | --- | --- |
| `tutorial` | 教程科普 | 6 |
| `tools` | 工具与创作 | 3 |
| `prompt` | Prompt 方法论 | 2 |
| `community` | 社区与平台 | 2 |
| `general` | 开发与综合 | 3 |

### 3.2 创作者 `PEOPLE`

```js
{
  id: "datawhalechina",
  name: "Datawhale",
  handle: "datawhalechina",
  followers: 35360,
  cat: "community",
  avatar: "D",
  tag: "国内最大的开源 AI 学习社区，教材与课程全部开源。",
  plat: ["公众号", "社区", "GitHub"],
  repos: [
    { n: "hello-agents", s: 87645, d: "《从零开始构建智能体》原理与实践教程" }
  ]
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 唯一标识，通常用 GitHub handle |
| `name` | string | 展示名 |
| `handle` | string | GitHub 用户名，可为空 |
| `followers` | number | GitHub followers 快照 |
| `cat` | string | 对应 `CATS.id` |
| `avatar` | string | 首字母占位，不依赖外链头像 |
| `tag` | string | 一句话定位 |
| `plat` | string[] | 主阵地类型 |
| `repos` | object[] | 代表项目，`n/s/d` |

### 3.3 链接与兜底

- `LINKS`：`id -> 主阵地 URL`；
- `EXTRA`：补充说明与无 GitHub 主号时的兜底文案；
- 没有稳定 URL 的平台（如公众号）只展示标签，不生成假链接。

### 3.4 数据规模

- 16 位创作者；
- 48 条代表项目；
- 快照时间：2026-11-23。

## 4. 视觉设计

### 4.1 色彩

| 变量 | 值 | 用途 |
| --- | --- | --- |
| `--paper` | `#ffffff` | 页面底色 |
| `--surface-sunk` | `#f6f6f4` | 次级背景 |
| `--line` | `#e7e7e5` | 分隔线 |
| `--line-strong` | `#d4d4d1` | 强调边框 |
| `--ink` | `#1d1d1b` | 主文字 |
| `--ink-2` | `#5c5b55` | 次文字 |
| `--ink-3` | `#8a887f` | 弱文字 |
| `--accent` | `#1f6b5a` | 主强调（深绿） |
| `--accent-soft` | `#e3efea` | 强调底色 |
| `--key` | `#9a5a08` | 次强调（棕金） |
| `--key-soft` | `#f6ecdc` | 次强调底色 |

整体是“纸张 + 墨水”的克制风格：白底、细线、低饱和绿，避免科技蓝紫的同质化。

### 4.2 字体

- 正文：`Noto Sans SC / PingFang SC / Microsoft YaHei / system-ui`
- 标题：`Noto Serif SC / Songti SC / Source Han Serif SC / Georgia`
- 等宽：`JetBrains Mono / SF Mono / Menlo`

标题用衬线，正文用无衬线，形成“编辑部手册”的气质。

### 4.3 形状与层次

- 圆角：`4 / 8 / 12 / 999px`；
- 阴影：`0 8px 24px rgba(20,20,18,.08)`，只用于浮层；
- 卡片以 1px 边框为主，不堆阴影；
- 分组用编号 `01–05`，强化目录感。

### 4.4 响应式

- `>1080px`：多列卡片墙 + 右侧信息；
- `≤1080px`：列数减少；
- `≤680px`：单列、搜索与筛选纵向堆叠；
- `prefers-reduced-motion`：关闭过渡动画。

## 5. 交互设计

| 交互 | 触发 | 行为 |
| --- | --- | --- |
| 搜索 | 输入框 `input` | 匹配姓名、handle、标签、项目名 |
| 聚焦搜索 | `/` | 聚焦并选中搜索框 |
| 分类筛选 | 点击分类 chip | 只显示该分类 |
| 主阵地筛选 | 点击平台 chip | 只显示含该平台的创作者 |
| 排序 | 切换排序 | followers / 默认顺序 |
| 详情 | 点击卡片 | 打开弹层，展示简介、主阵地、项目 |
| 关闭弹层 | `Esc` / 遮罩 / 关闭按钮 | 关闭并恢复焦点 |
| 空状态 | 无匹配 | 显示“没有匹配的创作者” |
| 视图切换 | 卡片 / 榜单 | 切换 board 与 rank |

关键实现入口：`visible()` 负责过滤，`render()` 统一重绘，`openModal()` 负责详情与焦点管理。

## 6. 技术实现

- 单文件 `index.html`：内联 CSS 与 JS，零依赖、零构建；
- 数据硬编码在脚本区，页面加载即渲染；
- 无后端、无外部 API、无 CDN；
- 头像用首字母占位，避免外链失效；
- 部署为静态文件，直接由 TraeSite 托管。

### 6.1 为什么不用框架

- 数据量小（16 人、48 项目）；
- 交互是过滤/排序/弹层，原生 JS 足够；
- 单文件便于部署与备份，也便于非专业维护者改数据。

代价是数据与视图耦合、缺少类型校验，见 §9。

## 7. 可访问性

- 搜索框有可读 label；
- 弹层打开后焦点进入弹层，关闭后恢复；
- `Esc` 可关闭；
- 装饰性箭头使用 `aria-hidden`；
- 支持 `prefers-reduced-motion`；
- 颜色对比以深墨绿/白底为主，正文对比充足。

待补：卡片键盘可达性、筛选 chip 的 `aria-pressed`、榜单表头语义。

## 8. 数据维护流程

1. 确认创作者是否符合收录标准；
2. 查 GitHub 主页与代表项目，记录快照日期；
3. 更新 `PEOPLE` / `LINKS` / `EXTRA`；
4. 若有公众号，只标注平台，不伪造主页链接；
5. 更新页脚快照；
6. 本地跑 `python scripts/check_site.py`；
7. 预览搜索、筛选、弹层、移动端；
8. 重新部署。

## 9. 已知问题

| 问题 | 影响 | 计划 |
| --- | --- | --- |
| 数据硬编码在 HTML | 难校验、易冲突 | P1 抽到 `data/creators.json` |

| 无深色模式 | 偏好 | P2 |

## 10. 路线图

### P1：可维护性

- 数据抽离为 JSON；
- 增加构建脚本，把 JSON 注入 HTML；
- 链接检查与 star 快照脚本；
- 卡片与筛选的键盘/ARIA 完善。

### P2：体验

- 深色模式；
- 创作者对比；
- 分享单条详情（URL hash）；
- 移动端底部筛选栏。

### P3：平台化

- 与公众号归档项目打通，展示每位创作者的最新文章；
- 数据 API 化，供其他页面复用。

---

## 11. 风险与边界

- 非官方整理，与创作者无隶属关系；
- followers/star 仅作参考，不代表质量；
- 公众号入口受微信限制，无法提供稳定公开主页；
- 收录与描述可能带主观判断，需在页脚声明口径；
- 不使用创作者头像外链，降低版权与失效风险。

## 12. 决策记录

| 编号 | 决策 | 理由 | 代价 |
| --- | --- | --- | --- |
| ADR-001 | 单文件静态页 | 零构建、易部署、易备份 | 数据与视图耦合 |
| ADR-002 | 以人为主体 | 与 star 榜形成差异 | 需要人工维护 |
| ADR-003 | 无 GitHub 主号也收录 | 覆盖社媒创作者 | 详情需兜底文案 |
| ADR-004 | 头像用首字母 | 避免外链与版权问题 | 视觉个性化弱 |
| ADR-005 | 不接实时 GitHub API | 避免限流与密钥 | 数据会过期 |
